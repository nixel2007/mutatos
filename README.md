# mutatos

Мутационное тестирование для OneScript.

Покрытие показывает, какие строки выполнялись во время тестов. Оно не отвечает на главный вопрос: а заметят ли тесты, если код начнёт работать неправильно? Мутационное тестирование отвечает — оно вносит в исходники небольшие изменения и смотрит, упадут ли тесты.

Если после замены `>` на `>=` все тесты остались зелёными, значит граница условия ничем не проверена, хотя строка и была покрыта.

## Установка

```sh
opm install mutatos
```

## Использование

```sh
mutatos run
```

По умолчанию мутируются исходники из `./src`, а тесты запускаются командой `oneunit` в текущем каталоге.

```sh
mutatos run -d src/core -p . --json out/mutations.json --min-score 70
```

| Опция                 | Назначение                                                                    |
| --------------------- | ----------------------------------------------------------------------------- |
| `-d, --directory`     | Каталог с мутируемыми исходниками, повторяемый. По умолчанию `./src`          |
| `-f, --file`          | Отдельный мутируемый файл, повторяемый                                        |
| `-p, --project`       | Каталог проекта, в котором запускаются тесты. По умолчанию текущий            |
| `--timeout-factor`    | Во сколько раз мутанту дают больше времени, чем исходному прогону. По умолчанию 3 |
| `--html`              | Путь к файлу отчёта в формате HTML                                            |
| `--json`              | Путь к файлу отчёта в формате JSON, схема mutation-testing-elements           |
| `--xml`               | Путь к файлу отчёта в разметке pitest (`mutations.xml`)                       |
| `--min-score`         | Минимальный индекс мутаций в процентах, иначе команда завершается с ошибкой   |
| `-j, --threads`       | Сколько мутантов проверять одновременно. По умолчанию по числу процессоров    |
| `--exclude-mutators`  | Мутаторы, не применяемые в прогоне, через запятую                             |
| `--all-tests`         | Проверять каждого мутанта всеми тестами, не отбирая по покрытию               |
| `--no-progress`       | Не показывать полосу прогресса                                                |

Тесты, которыми проверяются мутанты, отбираются теми же опциями, что и в OneUnit:
`-t/--tagsInclude` и `-T/--tagsExclude` по тегам, `-s/--testsuiteNameInclude`
и `-S/--testsuiteNameExclude` по наборам, `-m/--testMethodsNameInclude`
и `-M/--testMethodsNameExclude` по методам. Отбор применяется и к исходному прогону,
и к мутантам: иначе покрытие собиралось бы одними тестами, а мутанты проверялись другими.

Прогон долгий, поэтому в консоли идёт полоса с числом убитых и выживших и прогнозом остатка:

```
[=====================.............] 63/100  убито 48, выжило 15, осталось ~2 мин
```

Там, где консоли нет - прогон в сборке, вывод перенаправлен в файл - полоса заменяется
десятком отметок в логе.

Тесты прогоняются ядром OneUnit напрямую, минуя его командную строку: та поднимается сама и порождает дочерний процесс с ядром, то есть каждый прогон стоит двух стартов движка вместо одного. На мутационном прогоне, где запуск повторяется на каждого мутанта, это вдвое дольше.

Сборку точки входа при этом выполняет сам OneUnit — он собирает импорты тестов и сливает конфигурацию `oscript.cfg` из проекта и каталогов тестов, чтобы дочерний прогон видел те же зависимости, что и обычное тестирование.

Если OneUnit установлен в проект (`oscript_modules/oneunit`), тесты прогоняются его ядром, а не тем, что поставляется с mutatos: версия фреймворка остаётся за проектом. Указать ядро явно можно деталькой `mutatos.КаталогЯдраOneUnit`.

Если нужно вернуться к запуску через командную строку, задайте детальку `mutatos.СпособЗапускаТестов` значением `cli`.

```
  убито:            10
  выжило:           5
  без покрытия:     1

Выжившие мутанты - тесты не заметили эти изменения:

  examples/калькулятор/src/Классы/Калькулятор.os
    строка 17, Максимум: > заменено на >=
    строка 28, ВходитВДиапазон: И заменено на Или

    строка 28, ВходитВДиапазон: <= заменено на <

```

Ценность не в проценте, а в списке выживших: каждая строка — поведение, которое можно сломать, не уронив ни одного теста.

### Отчёты в файлы

`--html` пишет самодостаточную страницу: сводка, таблица файлов и исходник, в котором
мутации показаны прямо под своими строками, а сами строки подсвечены по исходу.
Ничего не тянет извне — открывается из письма и из артефактов сборки.

`--xml` пишет `mutations.xml` в разметке pitest: её читает плагин Mutation Analysis
для SonarQube, то есть мутационный индекс попадёт на дашборд без своей интеграции.
Полей, которых в OneScript нет — сигнатуры метода в терминах JVM, индексов байткода,
имени убившего теста — в отчёте нет: подделывать их значило бы врать инструменту.

`--json` пишет отчёт по схеме [mutation-testing-elements](https://github.com/stryker-mutator/mutation-testing-elements):
её понимают чужие инструменты мутационного тестирования, и к ней есть готовый
веб-просмотрщик.

Мутанты в строках, которые тесты не выполняют, попадают в «без покрытия»: убить их невозможно, поэтому они не прогоняются и не занижают индекс. Такой мутант говорит об отсутствии тестов, а не об их качестве — это область покрытия, а не мутационного тестирования.

Пример из вывода лежит в репозитории: `examples/калькулятор` — калькулятор с намеренно неполными тестами.

## Мутаторы

| Мутатор              | Что делает                                                     |
| -------------------- | -------------------------------------------------------------- |
| `Арифметика`         | `+` ↔ `-`, `*` ↔ `/`, `%` → `*`                                 |
| `Условия`            | `>` → `>=` и `<`, `<` → `<=` и `>`, `=` → `<>`, `<>` → `=`      |
| `Логика`             | `И` ↔ `Или`                                                     |
| `ОтрицаниеУсловия`   | `Если <условие>` → `Если Не (<условие>)`, то же для `Пока`      |
| `БулевыЛитералы`     | `Истина` ↔ `Ложь`                                               |
| `ЧисловыеЛитералы`   | `100` → `0` и `101`, `0` → `1`                                  |
| `СтроковыеЛитералы`  | `"текст"` → `""`, `""` → `"mutatos"`                            |
| `ГраницыЦикла`       | `Для Сч = 1 По N` → `По (N) - 1`                                |
| `Возврат`            | `Возврат <выражение>` → `Возврат Неопределено`                  |
| `УдалениеВызова`     | удаляет вызов процедуры целиком                                 |

Мутатор строковых литералов шумный: под него попадают и тексты сообщений, которые
проверять никто и не собирался. Выключается вместе с любым другим:

```sh
mutatos run --exclude-mutators СтроковыеЛитералы,УдалениеВызова
```

### Свой мутатор

Мутатор — класс с аннотацией `&Мутатор`. Контейнер находит его сам, ничего регистрировать не нужно:

```bsl
&Мутатор
Процедура ПриСозданииОбъекта(&Пластилин Токены)
КонецПроцедуры

Функция Имя() Экспорт
	Возврат "МойМутатор";
КонецФункции

Функция ТипыУзлов(Типы) Экспорт
	Результат = Новый Массив();
	Результат.Добавить(Типы.ВыражениеБинарное);
	Возврат Результат;
КонецФункции

Функция Мутации(Узел, Контекст) Экспорт
	Мутации = Новый Массив();
	Мутации.Добавить(Контекст.МутацияТокена(Имя(), Узел.Операция, "+", "заменено на +"));
	Возврат Мутации;
КонецФункции
```

`Контекст` умеет создавать мутации по токену (`МутацияТокена`) и по узлу целиком (`МутацияУзла`), а также отдавать текст исходника для токена и узла.

## Как это устроено

1. Исходник разбирается [osparser](https://github.com/oscript-library/osparser) в синтаксическое дерево.
2. Дерево обходится, каждый узел показывается мутаторам, подписанным на его тип.
3. Мутация — это координаты замены в тексте: позиция, длина и новый текст. Мутант собирается из оригинала применением ровно одной мутации.
4. Мутанты в непокрытых строках отсеиваются сразу — тесты их не выполняют и убить не могут.
5. Каждому оставшемуся подбираются тесты, которые выполняют мутированную строку: остальные прошли бы в точности как на оригинале.
6. Мутанты раскладываются по рабочим копиям проекта и проверяются одновременно, по числу процессоров: мутант — это отдельный процесс, который почти всё время тратит на старт движка, поэтому последовательный прогон простаивает.
7. Упавшие тесты означают, что мутант убит; зелёные — что выжил.

Исходники проекта не мутируются: мутант живёт в рабочей копии, поэтому прерванный прогон не оставляет проект в изменённом состоянии. Зависимости в копии не дублируются — копии показывается каталог библиотек оригинала.

Перед прогоном мутантов запускаются исходные тесты — с покрытием, которое и даёт карту выполненных строк. Заодно это проверка, что проект зелёный: на красном убитого мутанта не отличить от изначально сломанного кода. Длительность этого же прогона задаёт таймаут мутантам, иначе зациклившая мутация висела бы вечно.

### Отбор тестов по покрытию

Убить мутанта могут только тесты, выполняющие мутированную строку. Гонять на нём весь набор — значит платить за это на каждом мутанте, а мутантов сотни.

Чтобы понять, кто что выполняет, каждый набор тестов прогоняется отдельно со сбором статистики: один прогон движка отдаёт покрытие целиком и по тестам его не разделить. Отсюда и гранулярность — файл набора, а не отдельный тест.

Карта стоит по прогону на набор, зато экономит на каждом мутанте. На collectionos — 31 набор, 674 теста — это плюс минута к началу и вдвое меньше времени на самом прогоне.

Строка, которой в карте не оказалось, проверяется всеми тестами. Так же поступаем с набором, который в одиночку не проходит: он зависит от порядка выполнения, о его строках карта врала бы. Пропущенный набор превратил бы убитого мутанта в выжившего — это хуже, чем лишний прогон.

Отбор выключается опцией `--all-tests`.

## Разработка

```sh
opm install -l --dev
./oscript_modules/bin/oneunit e -d tests
```

Прогон самого mutatos на подопытном проекте:

```sh
oscript src/cli/main.os run -p examples/калькулятор
```
